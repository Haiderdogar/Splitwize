# Splitwize

Split bills with friends and groups. Firebase backend with Google Sign-In,
Cloud Firestore storage, and push notifications to everyone a bill is split with.

**Offline-first:** the app keeps its own SQLite database on the device, so it
works fully offline — create bills, split, mark paid, manage friends — and
syncs with Firebase when a connection returns. Firestore reads/writes are
kept to a minimum (delta sync, no listeners), which keeps the Firebase bill
tiny.

## Features

- **App icon & native splash** — custom icon (a receipt split between
  two friends on the teal gradient) shown centered on the native launch
  splash (light + dark + Android 12 variants)
- **Onboarding** — a 3-page animated intro (split bills · stay in the
  loop · offline sync) shown exactly once per install; Skip or
  "Get started" marks it seen (flag in secure storage, survives
  sign-out), then the normal sign-in flow takes over
- **Google Sign-In** — account created automatically on first sign-in
- **Friends** — find people by email, send an invite, they accept → connected
- **Groups** — create a group, invite from your connected friends, they accept to join
- **Split bills** — pick a group (or just friends), choose all or some members,
  split **equally**, by **percentage**, or with **custom amounts**
- **Settlement tracking** — each person's share shows Paid/Unpaid; the debtor
  taps "Mark paid" (or the creator taps "Mark received"); progress bars show
  e.g. 3/5 paid with the outstanding total
- **Currencies** — pick a default currency in Profile → settings (searchable
  picker with flags, via `currency_picker`). Every group has its own
  currency — set when the group is created, changeable anytime from the
  group screen — and each bill is stamped with it, so amounts always show
  the right symbol (Rs, €, $, …). Balances are tracked per currency and
  never mixed.
- **Dark theme** — full Material 3 dark theme across every screen;
  Profile → **Appearance** lets you choose **System default / Light /
  Dark** (per-device preference, applies instantly)
- **Polished async states** — shimmer skeleton placeholders while data
  loads (no spinner walls, no empty-state flashes on cold start),
  friendly error views with a working Retry everywhere data can fail,
  and every tap action (accept/decline/cancel/settle/sign-out…) guarded
  so failures surface as a message instead of a silent crash.
- **Balances** — running net per friend across all bills ("Sara owes you $12"
  / "You owe Ali $8"), with one-tap **Settle up** (marks all your outstanding
  shares with them paid) and **Remind** (sends them an inbox nudge)
- **Simplify debts** — Group Detail computes the fewest payments that
  settle the whole group (per currency, on-device, offline): mutual debts
  net out, chains collapse (A→B→C becomes a single A→C payment), and
  recording a payment marks the underlying bill shares as paid through
  the regular mark-paid machinery — no extra collections or rules
- **Receipt photos (optional)** — when creating a bill you can attach a
  photo of the receipt, from the camera or gallery. It is compressed
  on-device (max 1280px, JPEG quality 70 — typically 150–300 KB) before
  anything is uploaded, and stored in Firebase Storage. Works offline too:
  the photo is attached locally and uploaded when the bill syncs, then
  everyone sees it in the bill details.
- **Notification inbox** — bell icon with unread badge; bill creations,
  payments, friend requests and group invites all land here and deep-link
  to the right screen
- **Push notifications** — a Cloud Function notifies every participant
  (except the creator) the moment a bill is created, and notifies the creator
  when someone marks their share paid
- Material 3 UI with light/dark mode

## Offline-first architecture & keeping Firebase cheap

The app never reads Firestore directly — every screen streams from a local
SQLite cache (`lib/data/local_database.dart`, per-user DB file), which is
instant, free, and works fully offline.

- **Writes** apply to SQLite immediately (the UI updates at once) and enqueue
  a mutation in a local **outbox** table.
- **SyncService** (`lib/services/sync_service.dart`) listens for connectivity
  (via `connectivity_plus`) and, when online:
  1. **Pushes** the outbox in order — real user actions only, batched where
     possible. A bill created offline lands in Firestore on the next
     connection, and the Cloud Function fires at that moment, so participants
     get their push notification even if their app is closed.
  2. **Pulls deltas** — for bills, groups, requests and notifications it
     fetches only documents with `updatedAt` newer than the last pull (60s
     overlap for clock skew). Connections are the one full refresh, and their
     mirror docs are tiny (id + displayName, no profile reads). There are no
     snapshot listeners, so reads scale with *changes*, not with data size.
     Profile pictures/names for new people are cached on first pull.
  3. Soft deletes: rows are tombstoned (`deleted: true`) rather than deleted,
     so delta pulls can learn about removals and purge the local copy.
- Firestore's own disk cache is **disabled** (`persistenceEnabled: false`) —
  SQLite is the single cache, so nothing is fetched or stored twice.
- `AppRepository` (`lib/data/app_repository.dart`) is the only thing the UI
  and forms talk to; `FirestoreService` is now just the remote transport.
- The profile tab has a small **Sync** tile showing online/offline state,
  pending changes, and a manual "Sync now" button.
- **Secure storage** (`flutter_secure_storage`) holds the sensitive bits that
  must survive restarts without living in the plain database: the signed-in
  user's session snapshot (so the app opens straight into the home screen
  offline), the FCM push token, and a per-install device id. Signing out
  wipes the secure snapshot and the per-user SQLite file.

## State management (Riverpod 3 + code generation)

**Lists are lazy everywhere:** dynamic lists use `ListView.builder` /
`ListView.separated`, and multi-section pages (Friends, Groups, Group
Detail, Bill Detail, Create Bill, Create Group) are `CustomScrollView`s
whose sections are `SliverList.builder`s — Flutter only builds the
items currently on screen, so long friend/bill/member lists stay
smooth and light on memory. Onboarding uses `PageView.builder`.

**Responsive by construction:** no screen assumes a fixed phone size.
Text that shares a row with buttons or values sits in an
`Expanded`/`Flexible` (with wrapping detail rows as `Wrap`s), amounts
scale down with `FittedBox` instead of pushing layouts wider,
multi-line content lives in scroll views (onboarding pages scroll on
short/landscape screens), and dialogs cap their height to the
viewport. `test/responsive_overflow_test.dart` proves it: it pumps
all 13 screens — filled with deliberately long names, group titles
and amounts — at six sizes (320×568 up to a 1024×768 tablet, plus a
640×360 landscape) and at 1.6×/2.0× accessibility text scales, and
fails if any layout overflows. The decorative onboarding illustration
is pinned to 1.0× text scale (its labels are artwork; the real title
and body text scale normally).

**Functionally tested, not just reviewed:** `test/functional_*_test.dart`
run the *real* SQLite database (via `sqflite_common_ffi`) and the real
`AppRepository` / form notifiers — bill creation and outbox ordering,
paid-flag flips, per-currency balances and settle-up, the group
invite/accept/decline flow, the friend request lifecycle (including
re-keying a local request to its remote id), notification read flags
that survive pulls, split math for equal/percentage/custom bills, and
form validation. `test/unit_logic_test.dart` covers model
serialization round-trips, date parsing and money formatting.
Firebase-bound behavior (rules, Cloud Functions, FCM delivery) is
verified by review against the deployed configuration, since it
needs a live project.

## Continuous integration

GitHub Actions runs `flutter analyze` and the full `flutter test` suite on
pushes and pull requests targeting `main`, and can also be started manually.
Tests run one at a time because the functional suite shares a local SQLite
database. The workflow creates a temporary Firebase options placeholder for
static analysis; it does not contain or publish project credentials.

The workflow also builds three ABI-specific Android release APKs on pushes to
`main` and manual runs. Before the first build, add these repository Actions
secrets under **Settings → Secrets and variables → Actions**:

- `FIREBASE_OPTIONS_DART` — the full contents of your locally generated
  `lib/firebase_options.dart`.
- `ANDROID_GOOGLE_SERVICES_JSON` — the full contents of
  `android/app/google-services.json`.

Use the Firebase configuration for the Android app whose package name matches
`applicationId` in `android/app/build.gradle.kts`. The config files remain
ignored by Git and are written only into the temporary GitHub Actions runner.
Pull requests run analysis and tests but do not build with Firebase secrets.

After a successful run, open **Actions → Flutter CI → the workflow run →
Artifacts** and download `splitwize-android-apks-<commit>`. Install the APK
matching the test device: `app-arm64-v8a-release.apk` for most modern phones,
`app-armeabi-v7a-release.apk` for older 32-bit devices, or
`app-x86_64-release.apk` for x86-64 emulators. These APKs are for testing; the
Android release build currently uses the debug signing key and is not
Play-Store-ready.

- `flutter_riverpod` v3 with `riverpod_generator`: every provider is declared
  with `@riverpod` in `lib/providers/` and generated into `.g.dart`.
- **No `StatefulWidget` / `ConsumerStatefulWidget` anywhere.** Every screen
  is a `StatelessWidget`; a `Consumer` wraps only the subtree that actually
  displays changing state (lists, badges, buttons with busy state, …).
  Form fields just call notifier methods via `ref.read` and never rebuild
  on keystrokes.
- Form/dialog state lives in `@riverpod` Notifier classes
  (`CreateBillForm`, `CreateGroupForm`, `AddFriend`, `SignIn`,
  `GroupInviteSelection`, `TabIndex`) with immutable state + `copyWith`.
- After cloning, (re)generate the providers with:

  ```bash
  dart run build_runner build --delete-conflicting-outputs
  ```

### Firestore data model

| Collection | Contents |
|---|---|
| `users/{uid}` | `displayName`, `email`, `photoUrl`, `currency?` (default currency), `fcmTokens[]` |
| `users/{uid}/connections/{otherUid}` | accepted friends (mirror docs) |
| `connectionRequests/{id}` | `fromUid`, `toUid`, `status` (pending/accepted/declined) |
| `groups/{groupId}` | `name`, `createdBy`, `currency`, `members[]`, `invited[]` |
| `bills/{billId}` | `title`, `subtotal`, `tipPercent`, `total`, `splitType`, `createdBy`, `groupId?`, `participantIds[]`, `splits[]` (each with `paid`, `paidAt`), `currency`, `receiptImageUrl?`, `updatedAt`, `deleted` (tombstone) |
| `notifications/{id}` | `toUid`, `title`, `body`, `type` (bill_created/bill_paid/friend_request/group_invite), `billId?`, `groupId?`, `read`, `updatedAt` |

`updatedAt` (server timestamp) on every document powers the delta sync —
see `firestore.indexes.json` for the composite indexes the queries need.

## Firebase setup (do once)

### 1. Create the Firebase project
1. Go to https://console.firebase.google.com → Add project (e.g. `bill-splitter`).
2. **Authentication** → Sign-in method → enable **Google**.
3. **Firestore Database** → Create database → production mode → pick a region.
4. **Cloud Messaging** — no setup needed beyond the app config below.

### 2. Connect the Flutter app
```bash
dart pub global activate flutterfire_cli
flutterfire configure   # select your project + Android/iOS
```
This replaces `lib/firebase_options.dart` with real config and drops
`google-services.json` / `GoogleService-Info.plist` into place.
These project-specific files are intentionally ignored by Git; configure your
own Firebase project locally before building or running the app.

Android extras:
- Add your **SHA-1** (debug + release) under Project settings → Android app,
  otherwise Google Sign-In fails on Android. Debug SHA-1:
  ```bash
  keytool -list -v -keystore ~/.android/debug.keystore -alias androiddebugkey -storepass android -keypass android
  ```
- If the build complains about `minSdkVersion`, set it to **23** in
  `android/app/build.gradle`.

iOS extras (for push on iPhones):
- Upload an **APNs Auth Key** under Project settings → Cloud Messaging.
- In Xcode, enable the **Push Notifications** capability.

### 3. Deploy rules, indexes, functions & storage
```bash
npm install -g firebase-tools
firebase login
firebase use --add            # pick your project
firebase deploy --only firestore   # rules + the delta-sync indexes
cd functions && npm install && cd ..
firebase deploy --only functions
firebase deploy --only storage     # receipt photo rules (storage.rules)
```

### 3b. Receipt photo permissions (platform scaffold)

When you wrap this `lib/` in a Flutter scaffold (`flutter create .`),
add the camera/gallery permissions — `image_picker` needs them:

Android (`android/app/src/main/AndroidManifest.xml`):
```xml
<uses-permission android:name="android.permission.CAMERA"/>
```

iOS (`ios/Runner/Info.plist`):
```xml
<key>NSCameraUsageDescription</key>
<string>Take a photo of a receipt to attach to a bill.</string>
<key>NSPhotoLibraryUsageDescription</key>
<string>Choose a receipt photo to attach to a bill.</string>
```

Receipts are stored at `receipts/{billId}.jpg` in Firebase Storage and
linked from the bill document as `receiptImageUrl`.

### 3c. App icon & native splash (platform scaffold)

The icon (a receipt split between two friends, on the teal gradient —
`assets/icon/app_icon.png`, 1024×1024 master) and the native splash
(app icon centered on matching teal, via `flutter_native_splash`) are
configured in `pubspec.yaml`. Once the `android/` + `ios/` folders exist

```bash

dart run flutter_native_splash:create   # splash screens, incl. Android 12
```

Re-run both if you change the config (`flutter_native_splash:` /

## How push notifications work

1. On sign-in the app requests notification permission and saves the FCM
   token into the user's `fcmTokens` array (refreshed automatically; the
   token is also cached in secure storage).
2. Creating a bill writes it to the local SQLite cache instantly — and to
   `bills/{id}` in Firestore as soon as the device is online (immediately,
   or later via the outbox if you were offline).
3. `functions/index.js` (`notifyBillCreated`) triggers on that write, writes
   an inbox entry for each participant, and pushes:
   *“New bill: Dinner — Ali split 45.00 — your share: 15.00”*.
   This is why an offline-created bill still notifies everyone once it syncs —
   and their push arrives even with the app closed.
4. When a share flips to paid, `notifyBillPaid` triggers: the creator gets an
   inbox entry + push (*“Ahmed marked their 15.00 share as paid”*).
5. Friend requests and group invites write inbox entries directly from the app.
6. Dead tokens are pruned automatically. On sign-out the device token is
   removed so the next user of the phone doesn't get your pushes.

## Settlement tracking

Each entry in a bill's `splits[]` carries `paid`/`paidAt`. The debtor marks
their own share paid; the bill creator can mark anyone's share received (or
undo). Updates go through a Firestore transaction so concurrent taps can't
corrupt the array.

## Simplify debts

The Group Detail screen runs a debt-simplification pass over the group's
open shares (`lib/utils/debt_simplifier.dart`), separately per currency:
mutual debts between a pair are netted, remaining debts are routed along
chains so intermediate people drop out (A owes B, B owes C → A pays C once),
and anything left is listed as a direct payment. Every suggested payment
knows exactly which bill shares it settles, so recording it reuses the
ordinary mark-paid write (`bill.setPaid`) — there is no settlement
collection, no new sync op, and no rule change. When a routed payment
covers only part of a share, the share records the settled portion in
`paidAmount` (inside the existing `splits[]` entry) and flips to `paid`
when the remainder reaches zero; balances and outstanding totals always
use the still-owed remainder. The record button is offered to the
payment's payer or receiver, provided they participate in every bill the
payment touches (Firestore only lets participants update a bill).

## Balances

The Balances tab nets out **unpaid** shares across every bill you're in:
in bills you created, friends' unpaid shares count as them owing you; in
bills others created, your unpaid share counts as you owing the creator.
"Settle up" marks all your outstanding shares with one friend as paid (each
bill still fires its paid-notification to the creator); "Remind" drops an
inbox nudge on the friend who owes you.

## Monetization — ads + an Ad-Free subscription

**Ads are the revenue.** Everything in the app is free and unlimited —
bills, groups, and receipt photos included. The free tier shows one
AdMob banner under the Bills list (`AdBannerSlot` in
`lib/widgets/ad_banner.dart`). The app currently ships Google's
**test** ad ids (manifest / Info.plist / `Monetization`).

The only paid product is an **Ad-Free subscription** that removes the
ads, in two plans (`lib/utils/monetization.dart`):

- `splitwize_adfree_monthly` — $0.99/month
- `splitwize_adfree_yearly` — $7/year

- **Entitlement:** RevenueCat is the source of truth (`AdFreeStatus` in
  `lib/providers/monetization_providers.dart`, entitlement `adfree`),
  cached in secure storage so the tier is right offline. If the
  subscription lapses, the ads simply come back — nothing else
  changes; all bills and photos stay untouched.
- **Profile tab** has the Ad-Free tile that opens the paywall sheet
  (`lib/widgets/paywall_sheet.dart`) with both plans, Subscribe and
  Restore.

To activate checkout (do once, at store launch):

1. Create a RevenueCat project, add the Play/App Store apps, and create
   the two products above under the entitlement `adfree`, in one
   offering (monthly + annual packages).
2. Paste the RevenueCat public SDK key into `Monetization.revenueCatApiKey`.
   Until then purchases stay dormant and the paywall says checkout opens
   with the store launch.
3. Create an AdMob account/app, then replace the test app ids in
   `android/app/src/main/AndroidManifest.xml` and `ios/Runner/Info.plist`
   and the banner unit id in `Monetization.bannerAdUnitId`.

## Notes

- Friend search works by email — the other person must have signed in once
  so their profile exists in Firestore.
- Offline-created bills/groups get client-generated ids; if two people
  change the same bill while offline, the last synced write wins (fine for
  this scale; the paid-toggles use a Firestore transaction on push).
- The v1 offline calculator is preserved at
  `legacy/main_v1_local_calculator.dart` for reference.
